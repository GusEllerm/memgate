| 2026-09-25 | Label check semantics | An item is readable only if all its labels are allowed (item labels ⊆ allowed), not if any one is (Claude) | accepted (Gus, 2026-09-25) | "Any" admits an item tagged with one allowed and one locked label. See [[Label Rule Table]]. |

| 2026-09-25 | Portable filter form | Filter on precomputed label-set IDs inside the vector search, rather than on store-specific set operators (Claude) | accepted (Gus, 2026-09-25) | Works on every store surveyed and avoids needing the full list of labels. See [[Vector Store Label Filtering]]. |
| 2026-09-25 | Derived data labels | Derived items (summaries, consolidated facts, embeddings) carry the union of their sources' labels; permissive information-flow control is a later refinement (Claude) | accepted as default, with condition (Gus, 2026-09-25) | Condition: propagation must be relaxable per type of label. | 2026-09-25 | Label types and memory types: do labels have types with their own propagation rules, and do memory types change what may be relaxed? | Identity, location, principal, participants and session label types, each sticky or relaxable; episodic, semantic, procedural and personal memory types that decide which relaxations are allowed (Claude) | superseded by the rows below (Gus, 2026-09-25) | |

| 2026-09-25 | Who decides whether a label may be dropped when deriving memory? | The environment. | 2026-09-25 | What does high assurance guarantee? | Outbound only: nothing formed in a high-assurance location can be recalled outside it. | 2026-09-25 | Isolation of high-assurance locations | One shared store for all ordinary locations and personal memory; each high-assurance location gets its own partition (a Falda pool file, Qdrant shard key or Postgres partition, not a separate deployment). Start with one store, and design the API with a partition key so high-assurance partitions can be switched on later (Claude) | accepted (Gus, 2026-09-25) | Gus asked how ordinary locations would work with a store per location. Revised: only high-assurance locations are split out, and a query touches at most two partitions. See [[Label and Memory Types]]. |
| 2026-09-25 | Which policy engine? | Cedar for writing and proving policies: partial evaluation leaves a residual that becomes a query over the label-set table, then the ID list goes to the vector store. Drop relationship-based engines unless grants become relational (Claude) | accepted (Gus, 2026-09-25) | Cedar is the only engine that can prove the high-assurance seal; its partial evaluation is experimental.
