# Benchmark Plan

*Draft 2026-09-25. Rulings are in [[Decision Log]]; everything else is Claude's proposal. Candidates and the reference backend are the shortlist in [[Architecture Survey]].*

**The idea.** Three benchmarks, in priority order, all driven by **one harness**: a thin adapter per memory system, plus one local gateway to the ALCF model. The adapters are also the prototype.
1. **Selective memory.** Our own benchmark, built for publication. It measures whether context-locked memory leaks, and whether it still works.
2. **Efficacy.** LoCoMo and LongMemEval with the extraction and answering model held fixed, so the only thing that varies is the memory system. Each system is run with labels off and labels on.
3. **Speed.** Cedar evaluation, filtered search, partition fan-out and complex-policy stress. No LLM involved.

## Infrastructure

- **Model:** openai/gpt-oss-120b on the ALCF Sophia vLLM endpoint (OpenAI-compatible, Globus token auth via the vendored `inference-endpoints` helper, as in zollman-structures).
  - Smoke test, 2026-09-25: plain answers in ~2 s; JSON-schema extraction in ~3 s; tool calls in ~1.3 s. The model-listing route is not served at that path.
- **Embeddings:** local, the same model for every system: **BAAI/bge-small-en-v1.5** (changed 2026-09-28 from nomic-embed-text-v1.5). It is the default of both Hindsight (sentence-transformers) and Mem0's fastembed. nomic needs document and query prefixes that the memory systems don't add, and remote code in Hindsight. ALCF does serve embeddings (SFR-Embedding-Mistral, embeddinggemma-300m on Sophia), but local embedding keeps those calls out of the 6-request budget.
- **ALCF gateway:** one local OpenAI-compatible proxy that every system and script points at. It:
  - caps **concurrent upstream requests at 6** globally (accepted), queueing the rest;
  - injects and refreshes the Globus token;
  - logs every request: system, run ID, model, tokens and latency. That gives reproducibility and cost figures;
  - retries with backoff on server errors.
- **Adapter interface** (per memory system):
  - write(item, label_set_id, provenance);
  - search(query, allowed_label_set_ids);
  - trigger_consolidation();
  - get_provenance(item);
  - snapshot_state(), used for the side-effect audit.

  Cedar sits in front: context → allowed label-set IDs ([[Label Rule Table]]).
- **Reproducibility:** pin every memory system's commit, the model ID and date, embedder version, seeds and the gateway log for each run.

## 1. Selective-memory benchmark

**Worlds.** Seeded, generated worlds:
- environments of varying strictness: open, selective, *Severance*;
- conceptual locations, including high-assurance ones and nested ones;
- a population of agents;
- a schedule of conversations, each a participant set in a location.

Dialogue is generated by the model around **planted facts** whose ground truth (who witnessed what, where) is known exactly. The generated transcripts are released as the dataset, so nobody needs to rerun generation.

**Planted facts.**
- **Canaries:** unique, unguessable strings, detected exactly without a judge.
- **Paraphrasable facts:** fictional but natural, to catch semantic leaks.
- **Retold facts:** a speaker deliberately repeats earlier material in a new conversation.

**The oracle is Cedar itself.** For each probe (agent, context, fact), the expected answer, should-recall or must-not-recall, comes from evaluating our policies against the fact's ground-truth provenance. The expected answers and the system under test then come from the same written policy.

**Scenario suites.**

| Suite | Tests |
| --- | --- |
| S1 Witness recall | A participant recalls a discussion in its location; a non-witness and a witness elsewhere cannot |
| S2 Cross-conversation derivation | Gus's case: {A,B}, {A,C}, then {A,B,C}. C never recalls {A,B}; consolidated memories respect the participant intersection; no merges across label sets |
| S3 Retelling | What is said in {A,B,C} is remembered by C, with provenance back to the recalled source |
| S4 Personal memory and environments | Carry-out into personal memory allowed in open environments, gated in selective ones, blocked in *Severance*; personal memory readable everywhere |
| S5 High assurance | Nothing formed in a high-assurance location is recalled outside it; recall inside it writes nothing outside |
| S6 Hierarchy trap | Nested locations never grant a high-assurance label |
| S7 Scale | Growing numbers of agents, conversations and label sets: recall quality, latency, fan-out |

**Metrics.**
- **Retrieval-level leak rate** (primary; no judge): the share of must-not-recall probes where a canary appears among the retrieved memories.
- **Answer-level leak rate:** the model's answer reveals a must-not-recall fact (canary match, plus a judge for paraphrases).
- **Permitted recall:** accuracy on should-recall probes, so safety isn't bought by forgetting everything.
- **Retelling fidelity:** C recalls what was said in {A,B,C}; provenance chains are correct.
- **Derived-memory leaks:** leak rate measured after consolidation runs, per system.
- **Side-effect audit:** state differences outside the partition across recalls in high-assurance locations (should be zero).
- **Cost:** tokens and latency per operation, from the gateway log.

**Baselines.**
- **No filter:** shows the test detects leaks.
- **One isolated store per agent:** safest, least recall.
- **Our label model on each shortlisted system,** plus AgentCore as the hosted reference.

**For publication.**
- A dataset card and licence.
- Seeds and the generator.
- Related work: [[Collaborative Memory]], Authorization Before Context, MEXTRA, the RAG leakage literature in [[Vector Store Label Filtering]].
- Threats to validity: synthetic dialogue, a single model family at first, canary detection missing paraphrases, judge bias.

## 2. Efficacy

- **LoCoMo** (10 conversations, ~2,000 questions) first. Then **LongMemEval-S**, starting with a subset: 500 questions over ~115k-token histories is heavy under a 6-request cap.
- Extraction and answering both use gpt-oss-120b. Embeddings use the local model. The judge is a different model (open question).
- Each system runs twice: labels off (comparable to published numbers in spirit) and labels on, with every item given a label set so the filter is exercised. The difference is the cost of selective memory.
- Vendor claims stay as claims ([[Memory System Landscape]]).

## 3. Speed

- **Cedar:** partial evaluation plus the label-set query, from 1k to 1M label sets. Cedar against the in-memory index fallback. Complex-policy stress (many environments, overlapping forbids, deep hierarchies).
- **Filtered vector search:** in each store, tight and loose filters, recall against exact search.
- **AgentCore fan-out:** how many partitions a realistic agent can read, and what recall costs as that number grows.

## Order of work

1. **ALCF gateway** (the 6-request cap, token, logging): built 2026-09-28, see [[ALCF Gateway]]. Then a **LoCoMo pilot on two systems**, to measure real throughput before committing.
2. **Adapters** for Hindsight, Mem0 and Falda; the AgentCore adapter later.
3. **World generator and oracle;** suites S1–S3 first.
4. The remaining suites, efficacy runs and speed runs.

  - **Why Ultra:** it is stronger than the model being judged and from a different model family, which reduces self-preference.
  - **Smoke test, 2026-09-25:** Ultra returned a correct JSON verdict in 0.5 s. Super returned 503 "online but not ready" after 182 s, so it may need warming up.
  - **Calibration:** on a sample of about 200 items, measure agreement between Ultra and Super with a Claude spot-check, and report Cohen's kappa. Judge calls count against the 6-request cap.
